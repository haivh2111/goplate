📘 User Guide

goplate — a generator for Go REST APIs

Bootstrap services and scaffold features, adapters, and domain events that follow Folder-by-Feature + Ports & Adapters. Every generated file is wired, tested, and Swagger-annotated.

📦 Installation

Pick whichever install path matches your workflow. Goplate is a single static binary — no runtime dependencies.

Option A — go install (recommended)

$ go install github.com/haivh2111/goplate/cmd/goplate@latest

Lands at $GOPATH/bin/goplate. Requires Go 1.22+.

Option B — Pre-built binaries (no Go required)

Each release ships archives for darwin, linux, and windows on both amd64 and arm64. Grab yours from the Releases page.

# macOS Apple Silicon
$ curl -L https://github.com/haivh2111/goplate/releases/latest/download/goplate_v1.0.0_darwin_arm64.tar.gz | tar xz
$ sudo mv goplate /usr/local/bin/

# Verify
$ goplate --version
goplate version v1.0.0

Option C — Build from source

$ git clone https://github.com/haivh2111/goplate.git
$ cd goplate
$ make install     # → $GOPATH/bin/goplate
ℹ️

SHA256 checksums. Every release archive on GitHub Releases is accompanied by checksums.txt. Always verify before extracting: shasum -a 256 -c checksums.txt.

⚡ Quick start

From zero to a running API with one feature, one adapter, and one domain event — in about five minutes.

# 1. Verify the toolchain
$ goplate doctor

# 2. Scaffold a project
$ goplate new payment-service --module github.com/acme/payment-service --db postgres
$ cd payment-service

# 3. Start the database (postgres compose service)
$ docker compose up -d db

# 4. Scaffold a feature: model + dto + repo + service + handler + tests
$ goplate new-feature product --fields "name:string,price:float64,active:bool"

# 5. Wire it into server.go and migrate.go (the CLI prints the exact lines)

# 6. Run the server with hot reload
$ make dev

Now visit http://localhost:8080/api/health. Once you run make swag, Swagger UI is at /api/docs.

✨ goplate new

Materializes a complete service from the embedded boilerplate. Self-contained — no network or template-repo cloning required.

goplate new <project-name>
Scaffold a new Go REST API project
goplate new <project-name> [--module M] [--output O] [--db DB] [--no-git] [--no-env] [--skip-tidy]
FlagDefaultDescription
--module, -mgithub.com/<user>/<name>Go module path for the new project. The default uses your OS username.
--output, -o./Parent directory where the project is created.
--dbmysqlDatabase driver: mysql | postgres | sqlite.
--no-gitfalseSkip git init + initial commit.
--no-envfalseSkip copying .env.example → .env.
--skip-tidyfalseSkip go mod tidy (use when offline; you'll need to run it manually before make dev).

Example

$ goplate new payment-service --module github.com/acme/payment-service --db postgres
  ✓  Rendering template…
  ✓  Replacing module path → github.com/acme/payment-service
  ✓  Writing 22 files
  ✓  Copying .env.example → .env
  ✓  git init + initial commit
  ✓  go mod tidy

  Project ready at ./payment-service
  Next: edit .env, then run  make dev

What gets created

payment-service/ ├── cmd/ │ └── main.go # entry: load config → open DB → start Echo ├── config/ │ └── config.go # env-loaded Config ├── internal/ │ ├── server/ # Echo wiring, Providers, route + subscriber registry │ ├── middleware/ # JWT + error handler │ ├── shared/ # AppError, response helpers, validator │ ├── events/ # event bus + event types │ └── infra/database/ # GORM open + AutoMigrate ├── .env # copied from .env.example ├── .env.example ├── Makefile # dev / build / test / swag / migrate / gen-* ├── Dockerfile ├── docker-compose.yml └── README.md

🧩 goplate new-feature

Generates the eleven-file shape that constitutes a feature in goplate's hexagonal layout. Run from inside a project (the directory containing go.mod).

goplate new-feature <name> --fields "<dsl>" [--no-auth] [--no-pagination] [--dry-run]
FlagDefaultDescription
--fields, -f(required)Comma-separated model fields. See the Field DSL.
--no-authfalseOmit JWT middleware from generated routes.
--no-paginationfalseSkip ?page=&limit= on the List endpoint.
--dry-runfalsePreview without writing.

Example

$ goplate new-feature product --fields "name:string,price:float64,stock:int,active:bool"
  ✓  internal/features/product/model.go
  ✓  internal/features/product/dto.go
  ✓  internal/features/product/repository.go
  ✓  internal/features/product/repository_mysql.go
  ✓  internal/features/product/service.go
  ✓  internal/features/product/service_impl.go
  ✓  internal/features/product/handler.go
  ✓  internal/features/product/module.go
  ✓  internal/features/product/service_impl_test.go
  ✓  internal/features/product/handler_test.go
  ✓  internal/features/product/repository_mysql_test.go

  Next steps:
    1. Add product.Register(api, p) in internal/server/server.go
    2. Add &product.Product{} to internal/infra/database/migrate.go
    3. Run: make swag && make test

Routes registered

GET    /api/products        → List   (paginated unless --no-pagination, JWT-protected unless --no-auth)
POST   /api/products        → Create (JWT-protected unless --no-auth)
GET    /api/products/:id    → GetByID
PATCH  /api/products/:id    → Update (JWT-protected unless --no-auth)
DELETE /api/products/:id    → Delete (JWT-protected unless --no-auth)
⚠️

Manual wiring required. After generation, add product.Register(api, p) in internal/server/features.go and append &product.Product{} to the models slice in internal/infra/database/migrate.go. The CLI prints both lines.

🔌 goplate new-adapter

Generates a port (interface) and a concrete provider implementation under internal/adapters/<service>/. Re-running for a second provider AST-merges new methods into the existing port without losing your edits.

goplate new-adapter <service> <provider> --methods "<dsl>" [--stub-siblings] [--dry-run]
FlagDefaultDescription
--methods, -m(required)Method names or full Go signatures. See the Methods DSL.
--stub-siblingsfalseWhen the new run adds methods to an existing port, auto-append panic("not implemented") stubs to every sibling provider's adapter.go so the project keeps compiling.
--dry-runfalsePreview without writing.

Example — fresh adapter

$ goplate new-adapter payment stripe --methods "CreateCharge(req ChargeRequest) (*ChargeResponse, error); RefundCharge(id string) error"
  ✓  internal/adapters/payment/port.go
  ✓  internal/adapters/payment/stripe/adapter.go
  ✓  internal/adapters/payment/stripe/adapter_test.go

Example — adding a second provider

When port.go already exists, the run is smart:

  • Same methods as existing port → port.go untouched, only new provider files written.
  • New methods extend the interface → port.go is AST-merged (✎), existing provider stubs need updating (warning printed; pass --stub-siblings to auto-stub).
  • Same provider re-run → refused with a clear error (won't clobber your hand-edits).
$ goplate new-adapter payment paypal \
    --methods "CreateCharge(req ChargeRequest) (*ChargeResponse, error); ListCharges(ctx context.Context) ([]ChargeResponse, error)" \
    --stub-siblings
  ✎  internal/adapters/payment/port.go
  ✎  internal/adapters/payment/stripe/adapter.go     # ListCharges panic stub appended
  ✓  internal/adapters/payment/paypal/adapter.go
  ✓  internal/adapters/payment/paypal/adapter_test.go
ℹ️

Marker glossary. ✓ = created. ✎ = replaced (AST-merge or stub-append). ↻ = idempotent skip (already declared).

📡 goplate new-event

Registers a domain event constant + payload struct, and optionally scaffolds a subscriber in a target feature. Idempotent: re-running with an already-declared event is a no-op.

goplate new-event <EventName> [--payload "p:T,..."] [--subscriber feature] [--dry-run]
FlagDefaultDescription
--payload, -p(none)Comma-separated payload fields, same DSL as --fields. Empty → an empty payload struct.
--subscriber, -s(none)Feature that handles this event. Creates or updates internal/features/<feature>/subscribers.go.
--dry-runfalsePreview without writing.

Constant naming

The event-name PascalCase identifier is converted to a dotted lowercase topic:

EventNameTopic constant
OrderPlaced"order.placed"
PaymentFailed"payment.failed"
APIKeyRotated"api.key.rotated"

Example

$ goplate new-event OrderPlaced \
    --payload "OrderID:uint,UserID:uint,TotalAmount:float64" \
    --subscriber notification
  ✓  internal/events/event_types.go
  ✓  internal/features/notification/subscribers.go

On re-run with the same event name, the CLI prints ↻ ... already declared — left as-is for both files and exits zero. On a new event with the same subscriber, the existing RegisterSubscribers function gets the new Subscribe block spliced into its body — your existing handlers stay intact.

🔤 Field DSL

Used by --fields (new-feature) and --payload (new-event). Format: name:type,name:type,...

Supported types

Each type maps to specific GORM, validator, and Swagger tags. The mapping is the single source of truth — change a type, change all three tags.

DSL typeGo typeGORM tagValidator tagSwagger
stringstringnot null;size:255required,min=2,max=255string
int / int64 / uint(same)default:0min=0integer
float64float64not nullrequired,gt=0number
boolbooldefault:true(none)boolean
time.Timetime.Timenot nullrequiredstring

Examples

# Product with a price and a stock count
--fields "name:string,price:float64,stock:int,active:bool"

# Event with a timestamp — generated code automatically imports "time"
--payload "orderID:uint,occurredAt:time.Time"

Naming rules

  • Field names may be camelCase, snake_case, or PascalCase — they're normalised to PascalCase for the Go identifier and camelCase for the JSON tag.
  • Common acronyms (id, url, api, json, http, uuid) are preserved as ALL-CAPS in PascalCase: user_id → UserID.
  • Internal capitals are preserved: occurredAt → OccurredAt (not Occurredat).

⚙️ Methods DSL

Used by --methods on new-adapter. Auto-detects between two input forms based on whether the spec contains an open paren.

Form 1 — names only

Plain comma-separated PascalCase identifiers. Each becomes Name(ctx context.Context) error.

--methods "Send,SendBulk,Receive"

Generated interface:

type SmsGateway interface {
    Send(ctx context.Context) error
    SendBulk(ctx context.Context) error
    Receive(ctx context.Context) error
}

Form 2 — full Go signatures

Any valid Go interface-method signature is accepted. Separate methods with ; (commas would conflict with parameter lists).

--methods "CreateCharge(req ChargeRequest) (*ChargeResponse, error); RefundCharge(id string) error; ListCharges(ctx context.Context) ([]ChargeResponse, error)"

Behaviour:

  • Stdlib packages referenced via selectors (context.Context, io.Reader, time.Time) are automatically added to the port's import block.
  • Unqualified PascalCase types (ChargeRequest) are treated as user-defined and given type X struct{} placeholder stubs at the bottom of port.go for you to flesh out.
  • In the provider's adapter.go, local types are automatically qualified with the service package — ChargeRequest becomes payment.ChargeRequest in the receiver method signature.
💡

Validation comes free. Form 2 is parsed via go/parser. If your signature is malformed, Go's parser gives you the exact line/column with a helpful message — no custom DSL parser to learn.

🏗️ Architecture

Generated projects follow Folder-by-Feature + Ports & Adapters (Hexagonal Architecture). The generator refuses to produce code that violates the dependency direction.

Dependency direction

HTTP Request
    ↓
handler.go         // parse input, call service, return JSON
    ↓
service.go         // interface — the DI boundary
    ↓
service_impl.go    // pure business logic — no HTTP, no DB
    ↓
repository.go      // interface — the DB boundary
    ↓
repository_mysql.go// GORM queries only
    ↓
DB (mysql / postgres / sqlite)

// External services use the adapter pattern
service_impl.go → adapters/<service>/port.go → adapters/<service>/<provider>/adapter.go
ℹ️

Golden rule. A feature package may import an adapter's port (interface) but never a concrete provider package (stripe, paypal, …). Concrete wiring happens only in cmd/main.go and the Providers struct.

Conventions

ElementConvention
Package nameslowercase, no underscores (user, stripe)
Interface namesplain nouns (UserService, PaymentGateway)
ConstructorsNew<Type>, returning the interface
Event constantsEntityAction PascalCase → "entity.action" topic
Errorsshared.ErrNotFound / ErrBadRequest / ErrForbidden / ErrConflict — never raw errors.New in services
Responsesshared.OK(data) / shared.Created(data) — never raw c.JSON in handlers

🔄 End-to-end workflows

Bootstrap → first feature

$ goplate new order-service --module github.com/acme/order-service
$ cd order-service
$ docker compose up -d db          # or skip for --db=sqlite

$ goplate new-feature order --fields "total:float64,status:string"

# Wire it up (CLI printed the exact lines):
#   1. internal/server/features.go → add: order.Register(api, p)
#   2. internal/infra/database/migrate.go → add: &order.Order{}

$ make swag                            # regenerate Swagger
$ make test                            # verify generated tests pass
$ make dev                             # start with hot reload

Add a payment provider (later, you add a second one)

# First provider — fresh port + adapter
$ goplate new-adapter payment stripe --methods "CreateCharge(req ChargeRequest) (*ChargeResponse, error)"

# Wire in cmd/main.go + Providers struct (CLI printed the lines).
# Implement stripe/adapter.go with real Stripe SDK calls.

# Months later — add PayPal with the same interface. port.go is untouched.
$ goplate new-adapter payment paypal --methods "CreateCharge(req ChargeRequest) (*ChargeResponse, error)"

# Even later — PayPal needs ListCharges. Auto-stub stripe so the build stays green.
$ goplate new-adapter payment paypal \
    --methods "CreateCharge(req ChargeRequest) (*ChargeResponse, error); ListCharges(ctx context.Context) ([]ChargeResponse, error)" \
    --stub-siblings

Domain events

# Register the event with a notification-feature subscriber
$ goplate new-event OrderPlaced \
    --payload "OrderID:uint,UserID:uint,TotalAmount:float64" \
    --subscriber notification

# Publish from order/service_impl.go:
s.eventBus.Publish(events.OrderPlaced, events.OrderPlacedPayload{
    OrderID:     order.ID,
    UserID:      order.UserID,
    TotalAmount: order.Total,
})

🛠️ Troubleshooting

"not inside a Go module"

Generator commands (new-feature, new-adapter, new-event) must run from a project root or any descendant directory — they walk up looking for go.mod. If you see this, you're outside a Go module entirely. Run goplate new <name> first, or cd into an existing project.

"refusing to overwrite existing files"

The generator never silently clobbers user-edited code. Delete the listed files (or pick a different feature/provider name) and re-run. For adapters specifically, this only fires when the same provider is run twice — adding a new provider to an existing service is always allowed.

"port.go gained new methods — existing providers must implement them"

You ran new-adapter with a richer --methods set than the existing port. Two options:

  • Re-run with --stub-siblings to auto-append panic("not implemented") stubs to every sibling provider's adapter.go.
  • Manually update each sibling provider to implement the new methods.

Generated tests reference packages that don't exist yet

The feature templates expect internal/shared, internal/server, internal/middleware, and internal/events to exist in your project (they're scaffolded by goplate new). If you adopted goplate into an existing project, you'll need to create those packages — see the embedded boilerplate's structure for reference.

Building from source on a fresh machine fails at go mod tidy

Likely a network issue or a corporate proxy. Use GOPROXY=direct, or pass --skip-tidy to goplate new and run tidy later when you're back online.

Where can I see what would be generated without writing files?

Every generator command supports --dry-run. The dry-run output is byte-identical to what would land on disk, so you can pipe it through diff or just inspect visually.
