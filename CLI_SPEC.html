goplate CLI Suite

A developer tool for scaffolding, generating, and managing a production-ready Go REST API built on Echo, GORM, and hexagonal architecture — zero boilerplate friction.

Go 1.22+
Echo v4
GORM v2
Hexagonal Arch
Swagger / JWT

📋 Introduction

goplate is the companion CLI for the go-rest-api-boilerplate project. It handles two jobs: project bootstrapping (clone + configure a new service from the template) and in-project generation (scaffold features, adapters, and domain events that strictly follow the project's architectural rules).

🚀 What it solves

Eliminates the copy-paste cycle when adding a new business capability. Every generated file is already wired, tested, and documented.

🔒 What it enforces

Dependency direction, naming conventions, Swagger annotations, validation tags, and ≥80% test coverage scaffolding are built in — not optional.

Scope

This document covers the specification for two CLI entry-points:

  • goplate — standalone binary, used once to create a new project
  • make <target> — Makefile shims inside an existing project that delegate to the generator sub-commands

🏗️ Architecture Overview

The boilerplate follows Folder by Feature combined with Ports & Adapters (Hexagonal Architecture). The CLI generates code that respects this structure automatically. 

// Dependency flow — the CLI enforces this at generation time

HTTP Request
    ↓
handler.go         // parse input, call service, return JSON
    ↓
service.go         // interface — the DI boundary
    ↓
service_impl.go    // pure business logic — no HTTP, no DB
    ↓
repository.go      // interface — the DB boundary
    ↓
repository_mysql.go// GORM queries only
    ↓
MySQL (GORM v2)

// External services use the adapter pattern
service_impl.go → adapters/<service>/port.go → adapters/<service>/<provider>/adapter.go
ℹ️

Golden rule: a feature package must never import a concrete infra or adapter type. It may only import interfaces. The CLI generator will refuse to create code that violates this rule.

📦 Install the CLI

Install goplate once on your machine. It requires Go 1.22+ and git. No external build tools are needed beyond the standard Go toolchain.

Option A — go install (recommended)

$ go install github.com/haivh2111/goplate/cmd/goplate@latest

Option B — Build from source

$ git clone https://github.com/haivh2111/goplate.git
$ cd goplate
$ make install      # copies binary to $GOPATH/bin/goplate

Option C — Homebrew (macOS / Linux)

$ brew install haivh2111/tap/goplate

Verify installation

$ goplate --version
goplate v1.0.0 (go1.22.5, linux/amd64)

Prerequisites check

✨ goplate new — Create a Project

Bootstraps a new service from the boilerplate template. Clones the repository, replaces the Go module path, sets up the .env file, and runs an initial sanity check — all in a single command.

goplate new <project-name>
Scaffold a new Go REST API project from the boilerplate template
Scaffold
goplate new <project-name> [flags]
Flag Type Default Description
--module, -m string github.com/<user>/<name> Go module path for the new project
--output, -o string ./ (current directory) Directory where the project will be created
--db enum mysql Database driver: mysql | postgres | sqlite
--no-git bool false Skip initialising a git repository
--no-env bool false Skip copying .env.example → .env

Example

$ goplate new payment-service \
    --module github.com/acme/payment-service \
    --db mysql

  ✓  Cloning template…
  ✓  Replacing module path → github.com/acme/payment-service
  ✓  Copying .env.example → .env
  ✓  git init + initial commit
  ✓  go mod tidy

  Project ready at ./payment-service
  Next: edit .env, then run  make dev

What gets created

payment-service/ ├── cmd/ │ └── main.go ├── config/ │ ├── config.go │ └── .env.example ├── internal/ │ ├── features/ # user + auth included by default │ ├── adapters/email/ │ ├── infra/ │ ├── middleware/ │ ├── server/ │ └── shared/ ├── .env # copied from .env.example ├── Makefile ├── Dockerfile └── docker-compose.yml

🧩 new-feature — Scaffold a Feature

Generates the complete file set for a new business feature under internal/features/<name>/. Every generated file is already wired with the correct imports, interface stubs, Swagger annotations, and table-driven test skeletons.

ℹ️

Run this command from the project root. It can also be invoked via make gen-feature name=<name> inside an existing project.

goplate new-feature <name>
Generate all files for a new business feature (model → repo → service → handler → tests)
Generator
goplate new-feature <name> [flags]
Flag Type Default Description
--fields, -f string — Comma-separated model fields: name:string,price:float64,active:bool
--no-auth bool false Omit JWT auth middleware from generated routes
--no-pagination bool false Skip pagination on the List endpoint
--dry-run bool false Preview generated files without writing to disk

Example

# Using the CLI directly
$ goplate new-feature product \
    --fields "name:string,price:float64,stock:int,active:bool"

# Or via Makefile shortcut (inside project)
$ make gen-feature name=product fields="name:string,price:float64"

  ✓  internal/features/product/service_impl_test.go

  ✓  internal/features/product/repository_mysql_test.go

Generated files in detail

internal/features/product/ ├── model.go # GORM model with ID, CreatedAt, UpdatedAt ├── repository.go # ProductRepository interface ├── repository_mysql.go # GORM implementation (Create, GetByID, List, Update, Delete) ├── service.go # ProductService interface ├── service_impl.go # Business logic — calls repository via interface ├── dto.go # CreateProductRequest, UpdateProductRequest, ProductResponse ├── handler.go # Echo handlers with full Swagger annotations ├── module.go # DI wiring and route registration ├── service_impl_test.go # Table-driven unit tests using mockery mocks ├── handler_test.go # HTTP layer tests with Echo test recorder └── repository_mysql_test.go # Integration tests (SQLite in-memory)

Sample generated model.go

package product

import "gorm.io/gorm"

type Product struct {
    gorm.Model
    Name   string  `gorm:"not null;size:255"`
    Price  float64 `gorm:"not null"`

Sample generated dto.go

package product

type CreateProductRequest struct {
    Name   string  `json:"name"  validate:"required,min=2,max=255"`
    Price  float64 `json:"price" validate:"required,gt=0"`
    Stock  int     `json:"stock" validate:"min=0"`
    Active bool    `json:"active"`
}

type ProductResponse struct {
    ID     uint    `json:"id"`
    Name   string  `json:"name"`
    Price  float64 `json:"price"`
    Stock  int     `json:"stock"`
    Active bool    `json:"active"`
}

Manual steps after generation: register the feature in server/server.go and add the model to database/migrate.go. The CLI prints exact instructions with the correct import path after generation.

🔌 new-adapter — Scaffold an Adapter

Generates the port (interface) and a concrete provider implementation for an external service integration. Adapters live in internal/adapters/<service>/ and are always accessed via their port interface — never imported directly by features.

goplate new-adapter <service> <provider>
Generate port interface + concrete adapter implementation for an external service
Generator
goplate new-adapter <service> <provider> [flags]
Flag Type Default Description
--methods, -m string — Comma-separated method signatures to add to the port interface
--dry-run bool false Preview generated files without writing to disk

Example — Payment adapter (Stripe)

$ goplate new-adapter payment stripe \
    --methods "CreateCharge,RefundCharge,GetCharge"

# Or via Makefile shortcut
$ make gen-adapter service=payment provider=stripe

  ✓  internal/adapters/payment/port.go
  ✓  internal/adapters/payment/stripe/adapter.go
  ✓  internal/adapters/payment/stripe/adapter_test.go

  Next steps:
    1. Add  Payment PaymentGateway  to Providers in internal/server/providers.go
    2. Wire the concrete adapter in cmd/main.go
    3. Inject p.Payment into your feature via module.go

Example — Storage adapter (S3)

$ goplate new-adapter storage s3 \
    --methods "Upload,Download,Delete,GetSignedURL"

  ✓  internal/adapters/storage/port.go
  ✓  internal/adapters/storage/s3/adapter.go
  ✓  internal/adapters/storage/s3/adapter_test.go

Generated port.go

package payment

import "context"

// PaymentGateway is the port that features depend on.
// Features import only this file — never the concrete provider package.
type PaymentGateway interface {
    CreateCharge(ctx context.Context, req ChargeRequest) (*ChargeResponse, error)
    RefundCharge(ctx context.Context, chargeID string) error
    GetCharge(ctx context.Context, chargeID string) (*ChargeResponse, error)
}

type ChargeRequest struct {
    Amount   int64  // in cents
    Currency string
    Source   string
}

type ChargeResponse struct {
    ID     string
    Status string
}

📡 new-event — Scaffold a Domain Event

Adds a new domain event constant and payload struct to the event bus, then scaffolds a subscriber in the specified feature. Domain events decouple features — the publisher has no knowledge of who listens.

goplate new-event <EventName>
Register a domain event and optionally scaffold a subscriber in a target feature
Generator
goplate new-event <EventName> [flags]
Flag Type Default Description
--payload, -p string — Comma-separated payload fields: UserID:uint,Email:string
--subscriber, -s string — Feature that subscribes to this event (creates/updates subscribers.go)
--dry-run bool false Preview changes without writing to disk

Example

$ goplate new-event OrderPlaced \
    --payload    "OrderID:uint,UserID:uint,TotalAmount:float64" \
    --subscriber notification

# Or via Makefile shortcut
$ make gen-event name=OrderPlaced subscriber=notification

  ✓  Updated internal/events/event_types.go  (+OrderPlaced constant + payload struct)
  ✓  internal/features/notification/subscribers.go  (appended handler)

  Next steps:
    1. Publish the event in order/service_impl.go after a successful order
    2. Ensure notification.RegisterSubscribers(p) is called in server/subscribers.go

Changes to events/event_types.go

// Added by: goplate new-event OrderPlaced
const OrderPlaced = "order.placed"

type OrderPlacedPayload struct {
    OrderID     uint
    UserID      uint
    TotalAmount float64
}

Generated subscriber handler

// internal/features/notification/subscribers.go
func RegisterSubscribers(p *server.Providers) {
    p.EventBus.Subscribe(events.OrderPlaced, func(payload any) {
        data, ok := payload.(events.OrderPlacedPayload)
        if !ok {
            return
        }
        // TODO: send order confirmation email
        _ = data
    })
}

How to publish the event

// In order/service_impl.go, after order is persisted
s.eventBus.Publish(events.OrderPlaced, events.OrderPlacedPayload{
    OrderID:     order.ID,
    UserID:      order.UserID,
    TotalAmount: order.TotalAmount,
})

⚙️ Development Commands

All day-to-day development tasks are wrapped in the project's Makefile. Run make help at any time for a quick reference.

Server & Build
Run, compile, and hot-reload the service
$ make dev        # Start with air (hot reload on file change)
$ make build      # Compile binary → bin/api
$ make run        # build + execute (no hot reload)
$ make tidy       # go mod tidy — sync go.sum
$ make clean      # Remove bin/, coverage.out, coverage.html
Testing & Quality
Run tests, measure coverage, lint
$ make test       # go test -race -count=1 ./...
$ make coverage   # Run tests + open HTML coverage report
$ make lint       # golangci-lint run (installs if missing)
$ make mock       # Regenerate all mocks via mockery
💡

Coverage must remain ≥ 80% across all packages. make coverage prints the total at the end — CI will fail below this threshold.

Docs & Database
Swagger generation and auto-migration
$ make swag       # Re-generate Swagger JSON/YAML from annotations
                 # Output → swagger/ dir; served at /api/docs
$ make migrate    # Run GORM AutoMigrate (via go run ./cmd)
Generation Shortcuts
Makefile wrappers around goplate sub-commands
# Generate a new feature
$ make gen-feature name=product
$ make gen-feature name=product fields="title:string,price:float64"

# Generate a new adapter
$ make gen-adapter service=sms provider=twilio
$ make gen-adapter service=storage provider=s3

# Register a new domain event
$ make gen-event name=UserRegistered subscriber=notification
$ make gen-event name=PaymentFailed  subscriber=order

🔧 Configuration

The application is configured entirely via environment variables, loaded from .env on startup (via godotenv). The full reference is in config/.env.example. 

# ── Application ──────────────────────────────
APP_PORT=8080
APP_ENV=development       # development | production

# ── Database ──────────────────────────────────
DB_HOST=localhost
DB_PORT=3306
DB_USER=root              # required
DB_PASSWORD=secret        # required
DB_NAME=myapp             # required

# ── JWT ───────────────────────────────────────
JWT_SECRET=your-secret-key  # required — use 32+ random bytes in prod
JWT_ACCESS_DURATION=15m
JWT_REFRESH_DURATION=168h

# ── Adapters (optional) ───────────────────────
SENDGRID_API_KEY=           # if empty → console email adapter is used
EMAIL_FROM=noreply@myapp.com
STRIPE_SECRET_KEY=
S3_BUCKET=
AWS_REGION=ap-southeast-1
REDIS_URL=redis://localhost:6379
⚠️

Never commit .env — it is in .gitignore by default. Only .env.example (with placeholder values) belongs in version control.

🔄 End-to-End Workflow

A complete walkthrough from creating a project to shipping a new feature with tests and documentation.

1. Bootstrap a new project

Create the project

Run goplate new my-service --module github.com/acme/my-service to clone and configure the template.

Configure environment

Edit the generated .env — fill in DB credentials, JWT secret, and any adapter keys.

Start MySQL with Docker

Run docker compose up -d db to spin up a local MySQL instance defined in docker-compose.yml.

Start the dev server

make dev — the server starts with hot reload. Visit http://localhost:8080/api/docs for Swagger UI.

2. Add a new feature

Generate the scaffold

make gen-feature name=order fields="total:float64,status:string"

Wire it up in two files

Add order.Register(api, p) to server/server.go and &order.Order{} to database/migrate.go.

Fill in the business logic

Edit service_impl.go to add real logic; update repository_mysql.go for custom queries.

Regenerate docs and mocks

make swag && make mock — keep Swagger UI and test mocks in sync.

Verify coverage

make coverage — must remain ≥ 80%. Fill any gaps in the generated *_test.go files.

3. Integrate an external service

Generate the adapter

make gen-adapter service=payment provider=stripe

Implement the adapter

Fill in the generated stripe/adapter.go with real Stripe SDK calls.

Add the provider field

Add Payment payment.PaymentGateway to the Providers struct; wire the concrete adapter in cmd/main.go.

Inject into features

Pass p.Payment via the feature's module.go. The feature stores it as the interface type.

📖 Conventions

The CLI generates code that follows these conventions. Understanding them helps when editing generated files or filing bug reports against the generator.

📦 Package names

Lowercase, no underscores: user, auth, sendgrid, stripe.

🏷️ Interface names

Plain nouns: UserService, EmailSender, PaymentGateway.

🔨 Constructors

New<Type> pattern: NewUserService, NewMySQLRepository, NewAdapter.

🌐 Handler methods

HTTP verb + resource: GetByID, List, Create, Update, Delete.

📡 Event constants

<Entity><Action>: UserRegistered, OrderPlaced, PaymentFailed.

❗ Error handling

Return shared.AppError types. Handlers return the error; middleware maps it to HTTP status.

Error helper functions

import "github.com/acme/my-service/internal/shared"

// Use these in service_impl.go — never construct raw errors
return shared.ErrNotFound("product", id)
return shared.ErrConflict("sku already exists")
return shared.ErrForbidden("cannot modify another user's product")
return shared.ErrBadRequest("price must be positive")

Response format

// Always use shared helpers — never raw c.JSON in handlers
return c.JSON(http.StatusOK,      shared.OK(data))
return c.JSON(http.StatusCreated, shared.Created(data))

// Errors — return the error, middleware handles HTTP status
if err != nil {
    return err   // error_handler.go maps AppError → HTTP
}

📄 Generated File Reference

Quick lookup for what each generated file does and what you are expected to edit after generation.

File Responsibility Edit after gen?
model.go GORM struct with fields from --fields flag Add indexes, hooks, methods
repository.go Repository interface with CRUD methods Add domain-specific query methods
repository_mysql.go GORM implementation of all interface methods Implement custom queries
service.go Service interface mirroring repository operations Add business-specific methods
service_impl.go Business logic calling repository via interface Add validation, events, logic
dto.go Request/response structs with validation tags Tune validation rules
handler.go Echo handlers + Swagger annotations Rarely; add custom endpoints
module.go DI wiring and route registration Inject additional adapters
subscribers.go Event bus subscriptions for this feature Fill in handler logic
*_test.go Table-driven test skeletons with mock stubs Add test cases to reach ≥80% coverage
adapters/.../port.go Interface (port) for external service Add methods as needed
adapters/.../adapter.go Concrete provider implementation Implement all methods
💡

After any generation run: execute make swag && make mock && make test to ensure everything compiles, Swagger is current, and tests pass before you start editing the generated code.
